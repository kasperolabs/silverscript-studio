1. Identity

Committed once in the genesis payload as metadata. Permanent after launch.

Spec question: decimals 0 to 255

KCC-0021 allows decimals up to 255, but a token amount is an 8-byte KCC1 int (max 9,223,372,036,854,775,807). With 19 or more decimals, not even one whole token fits. Every value from 19 to 255 is unusable for any supply, so the bound could be 0 to 18, or the spec could say so where producers read it.

2. Supply

Mint policy: fixed. All of it is created at launch in one coin owned by you. The standard program has no mint entrypoint.

Spec question: KCC-20 says nothing about genesis or minting

The transfer conserves the total, but no section defines how supply comes into existence. Total supply is simply whatever the genesis outputs hold. A token whose program adds a mint entrypoint looks the same to a wallet unless it reads the artifact, so "fixed supply" is a promise this launchpad can only keep by deploying a program without one. Worth a Genesis section: what genesis states must satisfy, and how a consumer verifies supply.

Spec question: genesis skips the transfer's safety checks

The transfer entrypoint must reject successor states with an unsupported owner_scheme, so a transfer can't create an unspendable coin. Genesis outputs never pass through transfer. Nothing in KCC-20 stops a genesis from creating a coin with an unknown owner_scheme, a negative amount, or an invalid borrow_scheme. This launchpad validates them; the spec could require genesis states to meet the same rules.

Spec question: how many coins may a genesis create?

The default configuration caps a transfer at 3 token outputs. Whether that applies to genesis is not stated. An airdrop at launch (many holders in one genesis) depends on the answer.
